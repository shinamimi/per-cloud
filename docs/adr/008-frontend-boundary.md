# ADR-008 — 前后端职责边界：业务数据后端、UI 前端

> 日期: 2026-07-31
> 状态: 已接受

## 背景

前端曾大量硬编码"会变动的内容"：下拉选项、枚举中文标签、tag 颜色、按钮显隐规则。需明确前后端职责边界。

## 方案对比

| 维度 | 前端硬编码 | 全部后端下发 | 分类下发（本次决策） |
|------|-----------|-------------|--------------------|
| 改动成本 | 后端加枚举要改前端 | 前端实现复杂 | 按类型选合适方案 |
| UI 灵活性 | 高 | 低（样式也后端管） | UI 归前端，主题/国际化自由 |
| 数据一致性 | 低（易漏改） | 高 | 业务数据高 |

## 决策

**分类边界**：

| 数据类型 | 归属 | 方案 |
|---------|------|------|
| 业务枚举（状态/角色/操作类型） | 后端 | 统一字典接口 `GET /api/meta/options`，按 groups 返回 `[{value,label}]` |
| UI 样式（颜色/图标/Tag 类型） | 前端 | 主题/国际化自由，不进字典 |
| 动态业务数据（广告/VIP 套餐/系统配置） | 后端 | 独立业务接口，不进字典 |
| 权限能力（canDelete/canShare） | 后端 | 业务接口直接返回（资源相关，无法推导） |
| 基础操作显隐（角色+状态可推导） | 前端 | 集中规则表 `permissions/*.ts` + `can()` 推导函数 |

- 字典登录后拉取一次存 Pinia，不持久化
- 显示层混淆由后端做（OPERATOR→"管理员"、ADMIN→"超级管理员"），仅防非技术人员误解，角色定义不变
- axios 按后端控制器分类（`api/meta.ts`、`api/admin/*.ts`）

## 理由

1. 业务语义由后端单一来源，新增枚举无需改前端
2. UI 展示归前端，主题切换/国际化不依赖后端
3. 权限分两类处理：角色+状态可推导的（前端规则表）与资源相关的（后端返回），各取所长

## 影响

- 新增 MetaController + MetaService、字典 Pinia store
- 前端目录规范：`permissions/`、`components/common/`、按模块拆分的 `api/`
- 详细规范见 `frontend-standard.md`、`component-transfer.md`
