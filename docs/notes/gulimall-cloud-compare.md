# 谷粒商城机制 × 云盘对比（学习笔记）

> 目的：把谷粒商城的架构机制逐条对照云盘现有实现，找出"可借鉴加入 / 已具备 / 不适用"的项。
> 说明：谷粒是微服务电商（多服务跨库），云盘是单体 Spring Boot（单库），故对比对象是"机制"，不是"组件"。

| 机制 | 使用架构、框架（谷粒） | 使用架构、框架（云盘） | 解决什么 |
| --- | --- | --- | --- |
| 延迟队列 + 死信 | RabbitMQ 延迟队列 + 死信路由，订单 30 分钟未支付自动关单（订单/库存解锁） | Redis TTL 自过期 + @Scheduled 每日 cron 扫表（`FileCleanupTask` 03:00 回收站清理、04:00 分片清理）+ 访问时校验 `expire_time` | 防止过期任务/数据长期占用存储，实现到期自动回收 |
| 定时任务式清理 | 无扫表，事件驱动（MQ 消息到期触发） | 每日 03:00/03:30/04:00 cron 轮询：回收站过期物理清理、操作日志清理、打包产物与孤儿分片清理 | 防止存储与内存中过期数据累积（回收站 30 天、打包产物 24h、分片 TTL） |
| 幂等防重 | 数据库唯一索引（订单号唯一约束）+ Redis Set 存 MD5 防重 + 全局请求唯一 ID | 分片上传按 uploadId/分片号去重 + hash 秒传（相同内容直接命中已有对象） | 防止重复提交/重复下单/重复上传，避免重复扣减与重复占用 |
| 分布式锁 | Redisson 分布式锁 + 分布式信号量（秒杀库存预热、原子扣减） | 无分布式锁；单实例靠数据库原子操作（`ShareMapper` 原子下载计数 +1）与 Redis 计数 | 防止高并发下资源竞争（超卖、超下载、配额超扣）；云盘单实例下锁需求弱 |
| 消息可靠性 | 消息落库 + 定时扫描重发 + 生产者/消费者确认机制 | 无 MQ；上传元数据暂存 Redis（TTL）、打包下载任务为内存任务 + 产物对象存储 | 防止异步任务丢失导致业务未完成（打包、清理）；云盘靠任务重试与幂等兜底 |
| 异步任务 + 线程池 | 异步编排与线程池（秒杀异步建单、库存异步解锁） | `DownloadServiceImpl` 固定线程池（2 线程）异步打包 + WebSocket 进度通知 | 防止耗时操作阻塞主流程，提升响应 |
| 全文检索 | ElasticSearch 7（索引 + 聚合 + 过滤 + 排序） | MySQL `LIKE` 文件名模糊匹配（HLD 开放问题 3 预留 ES 引入） | 防止数据量大后 LIKE 检索慢、支持多维过滤；云盘数据量小 LIKE 已够 |
| 会话/登录态 | SpringSession + Redis 跨子域 Session 共享（多子系统 SSO） | JWT 无状态 Token + Redis 黑名单登出 | 防止多服务间登录态不同步；云盘单体 JWT 足够 |
| 分布式事务 | Seata AT（undo_log）+ 可靠消息最终一致（下单/锁库存/扣积分） | 单体 Spring `@Transactional` 本地事务 | 防止跨服务数据不一致；云盘单库无此问题 |
| 限流熔断 | Sentinel（QPS 限流、熔断降级、系统自适应保护） | 登录 5 次失败 Redis 计数锁定 15 分钟；无通用接口限流 | 防止接口被刷、单点故障雪崩；云盘可仅对关键接口做轻量限流 |

## 可加进 cloud 的优先级建议

| 优先级 | 机制 | 落点 | 理由 |
| --- | --- | --- | --- |
| 高 | 延迟队列/定时清理（保留现状） | 回收站、分享过期、打包产物 | 已用 cron+TTL 实现，功能达标；仅当"准实时回收"有要求再换 Redis ZSet 延迟队列，可选项 |
| 高 | 幂等防重 | 分片上传、创建分享、打包下载任务 | 已基本具备（uploadId+秒传）；建议分享创建也做防重，防连点 |
| 中 | 异步任务可靠性 | 打包下载产物回收、失败重试 | 可补"任务状态落库 + 失败重试"，与幂等配套，防内存任务丢失 |
| 中 | 轻量接口限流 | 上传/下载/登录/分享提取接口 | 用 Redis 计数做简单 QPS 限流即可，不必上 Sentinel |
| 低 | ES 全文检索 | 文件名/内容搜索（v0.2+） | 数据量达到"LIKE 慢"再引入，参照谷粒索引设计 |
| 不适用 | Redisson 分布式锁、Seata、SpringSession、RabbitMQ 集群 | — | 单实例单体架构，引入属过度设计；若未来拆微服务/多实例再评估 |
